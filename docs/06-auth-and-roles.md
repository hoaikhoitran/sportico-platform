# 06 — Auth and Roles

## Overview

Authentication is stateless **JWT Bearer**. Access tokens are short-lived; a long-lived refresh token (stored on the `users` row) is used to mint new access tokens. Authorization is **role-based** using ASP.NET Core `[Authorize(Roles = ...)]`.

## Registration & Email Verification

1. `POST /api/auth/register` with `{ email, password, fullName }`.
   - Creates a `User` with status `inactive` and an `EmailVerificationToken`.
   - Grants the `learner` role.
   - Sends a verification email containing a link to `{AppSettings:ApiBaseUrl}/api/auth/verify-email?token=...`.
2. `GET /api/auth/verify-email?token=...` sets the user to `active` and clears the token.

A user **cannot log in** until `active`.

## Login

`POST /api/auth/login` with `{ email, password }`:

- Verifies the password hash and that the account is `active`.
- Returns:

```json
{
  "isSuccess": true,
  "data": {
    "accessToken": "<JWT>",
    "refreshToken": "<opaque>",
    "expiresAt": "2026-05-27T10:15:00Z"
  }
}
```

### Access token claims

The JWT (generated by [JwtService](../src/SporticoApp.Infrastructure/Services/JwtService.cs)) contains:

| Claim | Value |
|---|---|
| `ClaimTypes.NameIdentifier` (`nameid`/`sub`) | User `Guid` |
| `ClaimTypes.Email` | Email |
| `ClaimTypes.Role` | One claim per role the user holds |

Token validation (`Program.cs`) enforces issuer, audience, signing key, and lifetime with **zero clock skew**. Access token lifetime is `JWT:AccessTokenExpirationMinutes` (default 15); refresh token lifetime is `JWT:RefreshTokenExpirationDays` (default 30).

## Refresh Token

`POST /api/auth/refresh-token` with `{ email, refreshToken }`:

- Validates that the stored refresh token matches, the account is active, and the refresh token has not expired.
- Issues a **new** access token and a **new** refresh token (rotation), updating the stored value.

> NOTE: The refresh request requires the `email` alongside the refresh token, because the token is looked up on the user identified by email.

## Roles

| Role | Granted by |
|---|---|
| `learner` | `POST /api/auth/register` |
| `coach` | `POST /api/coaches/register` (creates a coach profile and grants the role) |
| `admin` | Out of band (database seed / manual assignment). No self-service endpoint. |

A user may hold multiple roles simultaneously.

### Role-sensitive flows

| Action | Required role |
|---|---|
| Create / edit / archive a training package | `coach` |
| Approve / reject a training package | `admin` |
| Purchase a booking | `learner` |
| Request a training session | `learner` |
| Confirm / complete a training session | `coach` |
| Verify a payout account, approve/mark-paid a withdrawal | `admin` |
| Create a withdrawal | `coach` |

Beyond the role check, services enforce **ownership** (e.g. a coach can only confirm sessions on their own bookings; a learner can only see their own bookings). Ownership failures return `403` with a `*_NOT_OWNED` error code.

## Sending the Token

Send the access token on every protected request:

```
Authorization: Bearer <accessToken>
```

## Common 401 / 403 Causes

| Status | Likely cause |
|---|---|
| 401 | Missing/expired access token; account not `active`; invalid refresh token; clock skew (tokens validated with zero skew) |
| 403 | Authenticated but lacks the required role; or authenticated but not the owner of the resource (`*_NOT_OWNED`) |

## Swagger JWT Usage

Swagger UI is served at the application root (`/`) in all environments. To call protected endpoints:

1. Call `POST /api/auth/login` and copy `data.accessToken`.
2. Click **Authorize** (top right).
3. Paste **only the token** (no `Bearer ` prefix — the scheme is configured as `bearer`/JWT and the description says "Enter JWT token only").
4. Execute protected endpoints; Swagger attaches the header automatically.
